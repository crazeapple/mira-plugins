# sdd:start — 实现与流水线

把 TASKS.md 变成提交。两种推进方式：interactive 逐提案推进、unattended 流水线循环——**阶段内部行为完全一致**，差别只在阶段之间要不要交互。

## 流程

### 0. 来源检查（无任务不写码）

没有已定稿提案的任务上下文 → 退回 sdd:intake。来源链：需求 → 登记受理 → 定稿任务 → 授权写码；链条断在哪，退回到哪。

### 1. 领任务

查 REGISTRY「待实现」提案，依赖列含非完结提案的排除，按 P-XXX 序消费（编号序为默认序，依赖联查优先）。可取为空而「待实现」尚存 → 沿依赖列游走分诊：有环 → 点名环（interactive 停下问、unattended 总回报）；无环 → 逐个报等待原因（依赖未完结或挂起）：

- interactive：取用户点名的，或队首一个；完成后等待
- unattended：**流水线循环**——accept 完结回到这里取下一个；没有可取提案但 INTENT 池/探索中还有需求 → 回 sdd:intake/sdd:spec 补一个待实现提案（池中判直做的块直接做掉完结，不经 spec）→ 继续开发；彻底没有可取 → 总回报收尾（做了什么、挂起了什么、被依赖阻塞了什么）

### 2. 工作区

主会话切 `dev/<codename>` 分支 + worktree 隔离（分支拓扑：`references/git-flow.md`）——分支与 worktree 由主会话建删，子 Agent 只在其内干活（路径入简报）。

### 3. 派发实现（默认提案级子 Agent）

实现循环派给子 Agent 执行（简报与回收核验：`references/dispatch.md`）；子 Agent 按 TASKS.md 中登记的顺序完成任务，**中间不停顿、无需用户确认**；interactive 的交互点在提案边界（启动开发=派发、回收报告后等待）：

- 实现 → 以任务为界提交：**一个任务一个提交**，单提交不混多任务
- 提交信息公开面零治理：主题行无治理 ID、**无 footer**；任务↔commit 映射由主会话回填 TASKS.md「完成」列
- 提交前过门禁（程序：`references/gate.md`，bootstrap 指针目标——任何时候的提交都先读它）
- Agent 照常自检（跑构建、跑测试是开发常识）——但**正式验证闸门只有提案末端一道**（sdd:accept 的契约核验），不在任务间设停
- 子 Agent 只产出提交：不碰治理记录、不建删分支，发现设计问题停下上报，不就地改设计
- 派发期间主会话照常受理与探索其他提案（sdd:intake、sdd:spec 不受阻）；回收通知到达优先处理——先核验回填，再回到手头事务

派发不可用（无子 Agent 机制或同一提案派发连续两次中断）→ 主会话按同一纪律直做，程序不变。

### 4. 并行加速（仅用户明确要求时）

任务级（同提案无依赖任务分派多子 Agent）或多提案级（多个互不依赖的可取提案同时推进），程序见 `references/dispatch.md`。未经用户要求的并行 = 违规；单提案默认派发（第 3 步）不算并行。

### 5. 收尾与移交

- 全任务完成、TASKS.md 完成列填齐 → REGISTRY 状态：待验收 → 调 sdd:accept
- **开发中发现设计需要推翻**：走放弃流程（`references/git-flow.md`「放弃」节）——记 AMENDMENTS（为什么换/换成什么）、提交丢弃、dev 分支删除 → 回 sdd:spec 重来。**禁止边开发边改设计**——设计漂移会让实现与规格脱节

## 常见误区

| 你会想 | 事实 |
|---|---|
| 「这个改动太小，不值得走任务」 | 小 = 三问分流判直接做的依据；一旦受理，就没有「太小的任务」 |
| 「顺手把 T03 里的一点活带到 T02 的提交里」 | 提交混任务 = 回滚失效 + 证据指认失效；多一行代码也不行 |
| 「设计这里不对，我边写边改，最后同步文档」 | 设计漂移会让实现与规格脱节；要么按图施工，要么走放弃流程重来 |
| 「同时开三个 worktree 效率高」 | 并行仅在用户明确要求时；派发要带核验（references/dispatch.md） |
| 「挂起的提案先放着，分支别动」 | 对——挂起不动任何分支；恢复时 accept 会重立基线 |
