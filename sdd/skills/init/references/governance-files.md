# governance-files.md — 治理文件规则

本文件是治理文件的规则与布局。模板在 `sdd:templates/tmpl-*.md`（tmpl-registry、tmpl-intent、tmpl-journal、tmpl-amendments），是结构参照——占位条目与占位行示意条目形状，不随文件落盘；落盘的永远是实例；所有技能引用本文件与模板，不得另行定义格式。写入：目标文件不存在，按对应模板整建（H1 与条目形状一并落，占位处填真实数据）；已存在，按模板条目形状追加；树 schema 低于插件版本时的首建直接用当前模板，不视为混版。读取：INTENT/JOURNAL/AMENDMENTS 不存在视为空。命名规则：容器单数（REGISTRY/INTENT/JOURNAL），条目集复数（AMENDMENTS）。

## 治理根布局

```text
<治理根>/
├── REGISTRY.md      # 执行维度：提案表 + 配置区 + schema 版次
├── INTENT.md        # 需求维度：意图池，全部意图一个区块
├── JOURNAL.md       # 探索底稿：澄清、探索、选定与否决、拆分依据
├── AMENDMENTS.md    # 已生效方案被推翻/取代的修正登记
└── proposals/
    └── P-XXX/
        ├── P-XXX-SPEC.md
        ├── P-XXX-DESIGN.md
        └── P-XXX-TASKS.md
```

- 布局规则：治理根根上 REGISTRY 必在（init 出生），INTENT/JOURNAL/AMENDMENTS 首写出现（存在 ⇔ 至少一条真实条目）；提案内三文件带提案号前缀（跨提案并列使用——编辑器标签、搜索、聚合——时自标识）
- **治理文档不写本机信息**：仓库外的本机信息（项目外路径、主机名、用户名等）不入文档——治理树随仓迁移（换机 clone、他人 clone、standalone 推私有远端），这些信息不成立，还泄露本机环境；引用项目内资源一律用项目内相对路径；用户原话逐字引用不受此限
- **spec 之前的过程留痕只在一处：JOURNAL**。意图的澄清、方案成形（选定与否决）、拆分依据（`[I-XXX]` 头），提案的细化探索（`[P-XXX]` 头），判直做修复的留痕（`[I-XXX]` 澄清条目），全部追加于此；INTENT 区块只存事实（原话、状态、一句话边界结论），永不承载过程文本
- 各技能正文的语义引用（「SPEC 契约表」「按 TASKS 序」）为简称，不构成对前缀规则的偏离

## 治理仓提交（standalone）

- 一笔提交只含一个关注点，不混合不同关注点的改动
- 状态迁移即时提交；探索、回填等过程性写入在一次响应收口时合为一笔
- 开始写一个新关注点之前，先把上一个关注点的未提交改动提交掉
- inline 形态不适用：治理改动留在工作区，提醒用户随项目仓提交

## REGISTRY

模板：`sdd:templates/tmpl-registry.md`。

- **配置区**（frontmatter 字段，枚举第一个值即默认）：`mode: unattended / interactive`（推进方式）；`verification: auto / manual`（提案末端验收执行者）；`versioning: semver / calver`（发布版本方案，init 时定——公开契约）；`sdd-kind: standalone / inline`（init 时定，不可变）；`schema` 是**治理结构的版本戳**，值取自 sdd 版本（模板对齐判据）；模板中的 schema 行与插件版本同步
- **提案表**：`intent` 列是提案的归属标记——兄弟提案、意图完结推导、按意图聚合看板都查这里；`内容` 一句话，与提案文件 H1 `<标题>` 同源；`依赖` 列静态声明依赖的提案号（无写 `—`，多个顿号分隔）——不清除、不标记满足，发号后新发现的依赖就地补登；调度联查：依赖含非完结提案的不进实现队列（start 领任务排除）；登记与补登做环检测——沿依赖列游走（非完结节点），回到自身即环 → 停下问，不得落盘（环属依赖声明错误，修复方向由人裁决）；提案状态（闭集）`立项 → 待实现 → 待验收 → 验收中 → 完结`，旁路 `挂起`；状态迁移即时同步；行只增不删（废弃标挂起或完结）
- 需求维度不在 REGISTRY——看 INTENT.md（需求完结 = 意图名下提案全完结，推导回写）
- 任务明细**不进** REGISTRY（单源在提案的 TASKS.md）

## INTENT

模板：`sdd:templates/tmpl-intent.md`。

- 一个意图一个区块：ID 递增追加，区块不删；状态在区块头原位更新（随手）
- **原话逐字保留**（引用块包裹），不改写不概括；区块标题里的短标题是 intake 提炼的索引名，非原话改写
- 状态闭集：`记录 → 澄清中 → 已拆分 → 完结`（完结由名下提案推导，accept 清理时回写；或判直做且完成，完成时回写——判定时边界结论随手注明直做），旁路 `已否`（澄清中被否决、用户撤回、判直做未做而另起意图时落——边界结论记因；否决不立项专用）
- 边界结论一句话，随手更新；已否/完结的区块原样保留
- 已拆分/完结的区块带 P 表格，一行一个提案（提案号 + 内容一句话）；与 REGISTRY 提案表同次写入，状态不进此表（单源在 REGISTRY）
- I 包含 P：一个意图经澄清拆分为 1..n 个提案，意图是需求全程的源头；提案归属登记在 REGISTRY 提案表 `intent` 列，兄弟查询与聚合都查那里

## JOURNAL

模板：`sdd:templates/tmpl-journal.md`。

- **spec 之前的一切过程只落这里**（单点，无第二留痕处）
- 槽位即条目正文的固定形状：按条目类型齐备落槽，暂无内容写「无」；追加不重写
- **决策必须各有条目**——方案选定、否决（含否因）、拆分依据，一条不许少，不留痕即流程违规
- 条目头按书写当时所属实体落：提案不存在前不可能有 P 头；归属模糊宁 I 不 P
- **判直做的修复以 `[I-XXX]` 澄清条目留痕**（判直做即记）：问题入已知信息与约束、成功标准一行（轻量验收句）、取舍一行（无则不写）；记 git 看不见的部分
- **不记完成映射**：任务↔commit 是 TASKS 的职责，JOURNAL 不记；正文引用 commit 作因果上下文（记因不记果）合法
- 揭示性结论同时落进产物（DESIGN 决策表/被否备选表）——过程留在探索底稿防遗忘，结论进产物防重犯

## AMENDMENTS

模板：`sdd:templates/tmpl-amendments.md`。

- **生效 = 提案定稿**：定稿起方案开始管事，此后的推翻与取代登记于此；定稿前的变更自由
- 触发条件（三分支）：
  1. spec 期内（未 start）变更 → **不记**，直接修改 + SPEC.md 头部 `version` 自增
  2. 开发中（start 后未 accept）推翻已生效方案 → **记**，提交丢弃、dev 分支删除，回退 spec 重来；**禁止边开发边改设计**
  3. 已 accept 完结的提案被新提案以另一方案取代 → **记**；旧提案冻结不动（完结即历史文物）
- 治理形态/规则本身（编号规则、状态词表、契约判据、目录形态）的演变**不进** AMENDMENTS——走本插件仓库的 CHANGELOG
- 条目号 `AM-NN` 递增，追加式永不重写

## 编号规则

- `I-XXX`：意图，全局递增，不复用
- `P-XXX`：提案，全局递增，按依赖顺序发号（发号时点已知的依赖）——被依赖的提案先号；不复用、不重排；发号后新发现的依赖经提案表依赖列兜序
- `P-XXX-TNN`：任务，提案内递增

## 看板读法（只读聚合）

问进度时，顶部先报治理头：`sdd` + REGISTRY 配置区五项（mode、verification、versioning、sdd-kind、schema）。
然后按意图聚合——池深（记录 n / 澄清中 n）、已拆分意图名下各提案状态计数、完结意图数；再列出挂起提案及原因。不展开任务明细。
