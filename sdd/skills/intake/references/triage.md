# triage.md — 三问判据与拆分判定

## 三问判据细则

**① 期望行为与现状有差异吗？**
用户描述的状态是否已是事实：纯咨询（「这个怎么用」）判「无」——池外一闸，答完即走；「这个坏了」是期望≠现状，判「有」，走直做车道。判不准时的处置：interactive 问用户一句分类——咨询、直做、需求三选一；不定或 unattended，受理入池（判断推迟到澄清，不是裁定；多受理的成本是一次澄清，漏受理的成本是走样）。

**② 达成方式有方案空间需要收敛吗？**
实现路径是否唯一到没有选择余地（「把 typo 改了」无空间；「加个导出功能」有格式/入口/范围等空间）。注意：有方案空间 ≠ 要用户选——澄清成形的职责就是收敛空间。

**③ 完成标准用户一听就自明吗？**
「改好这个 typo」自明；「让页面好看点」「优化下性能」不自明。不自明 = 需要验收标准表 = 必须受理。**这条最容易拦住「顺手改」走样。**

**直做车道限界**：直做仅限不增加功能的修复与维护——现有验收契约内的工作；凡需要新验收标准的（新能力、行为面变化），一律立项走 spec。

## 拆分判定（澄清收敛后）

**判据：交付物是否共享同一验收契约。**

- 共享 → **一个提案，多个任务**（同类重复不拆：十处校验是一个需求的十个任务）
- 各自独立验收 → **多个提案**，同挂一个意图（如「支付」= 接入 + 对账 + 退款 → P-001/P-002/P-003，同属 I-02）

拆分动作（详见 intake SKILL 第 3 步）：JOURNAL `[I-XXX]` 记拆分依据 → 建提案目录 → REGISTRY 提案表加行（intent 回指）。拆分依据必须留痕——为什么是这两个交付物，有据可查。

## codename 生成规则

- 标题（或目标短语）转 kebab-case：`支持深色主题` → `dark-theme`；`修复导出崩溃` → `fix-export-crash`
- 英文标题直接小写连字符；中文取关键词意译英文
- 全局唯一（查 REGISTRY 提案表 codename 列去重；撞了加序号 `-2`）
- codename 用在公开面（分支名、worktree 目录名）；提案目录名用 P-XXX
