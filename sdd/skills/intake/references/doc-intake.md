# doc-intake.md — 需求文档受理

用户给的是成文材料（文件或目录，含路径，一至多份，体裁不限——PRD、会议纪要、邮件、聊天导出）。材料确认落位后即完成使命：**不冻结、不收编、不入库**——它的内容已分解进治理文档，原件留在用户手里。

落进治理文档的是内容本身：无导入叙述（不写「根据提供的文档」）、无来历口吻（不写「文档中指出」）、无外部文件引用。

## 流程

### 1. 拆成条目

通读材料，拆成条目清单：每条一句可判定的诉求/约束/信息。给每条临时编号（D1、D2…便于指认）。

### 2. 逐条定去向

对每一条给出显式去向，**不能少也不能多**：

| 条目类型 | 去向 |
|---|---|
| 新诉求 → 三问判需求/维护 | 立项 / 直接做 / INTENT 池 |
| 与既有提案相关（补充/修正） | 对应提案的 JOURNAL 追加（未定稿）或走变更流程（已定稿） |
| 背景信息、约束 | JOURNAL 探索底稿（挂对应意图/提案头） |
| 重复（与存量治理数据已有的相同） | 标注重复来源，不重复落 |
| 无法落位的 | **列出来问用户**，不猜 |

- mode=interactive：逐条列出定好的去向，等用户确认后落位
- mode=unattended：自动定去向并落位 + **差异报告**——多出（材料有、治理数据中无着落）与缺失（治理数据中该有、材料没覆盖）逐条列出，停驻项标出，不停下等确认

### 3. 核对

定去向前先与存量治理数据过一遍：REGISTRY 现有提案、INTENT 现有条目——材料与治理数据的差集就是「多出/缺失」的报告来源。

### 4. 批量落位

按确认结果执行：捕获得 `I-XXX`、澄清或直接拆分（走 SKILL.md 第 2-3 步）、JOURNAL 追加、INTENT 区块更新。落位完成后回报：落了几条、各去了哪、多出/缺失清单。
