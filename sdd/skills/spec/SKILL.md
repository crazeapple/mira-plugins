# sdd:spec — 写规格、契约与定稿

把 JOURNAL 里的澄清与探索底稿整理成可核对的规格：SPEC（背景/范围/边界与异常/契约）、DESIGN、TASKS。输入是意图池 + 探索底稿，产出是 start 的唯一依据——这里含糊一分，实现走样一丈。

## 流程

### 0. 前置

无提案上下文 → 退回 sdd:intake。有提案 → 读 JOURNAL（`[I-XXX]` 澄清成形段 + 本提案 `[P-XXX]` 段）+ INTENT 区块。**方案没定（底稿没结论、DESIGN 将有待定）→ 退回 sdd:intake 细化探索——本技能只成文，不探索；写的过程中冒出没定的事同样退回，不自行定案。**

### 1. 写 P-XXX-SPEC.md

- frontmatter：`version: v1`（提案级版本，定稿后变更自增）+ `intent: I-XXX`（来源意图静态回链）
- **背景**：问题与目标——从意图边界转写；细读指路 JOURNAL 对应段
- **范围内 / 范围外**（范围外必写，防蔓延）
- **边界与异常**：空态、错误、边界输入下的行为——验收标准的另一半来源
- **验收标准表**（契约，规则见 `references/contract.md`）：逐条绑定**可独立执行的验证命令**（UI 行为的命令即 E2E 测试，用例随本提案任务创建）；不可核对表述（「好用」「美观」）**退回重写**——可核对是契约的底线，一条都不许混入

### 2. P-XXX-DESIGN.md

- **方案概述**：一句话定案；**接口 / 数据 / 关键流程**三维度展开（各可一句话）
- 关键技术决策（每条：决策 + 理由）
- **被否备选留档**：方案 + 否因——成形期否决的选项来自 JOURNAL 对应条目，防止三周后换个措辞重新发明已否方案

### 3. P-XXX-TASKS.md ← DESIGN.md 派生

- 任务 = **一个提交粒度**（做完即可提交的单元）
- 被依赖的任务排前
- 每任务标注覆盖的验收条目（编号对应契约表）

### 4. 定稿检查

四条**全过**才准定稿：

1. 验收标准全部可核对（每条有绑定验证）
2. 范围边界清楚（范围内/外都成形）
3. 方案已定（DESIGN 无「待定」）
4. 任务表就绪（任务覆盖全部范围内条目，无孤儿标准）

- 不过 → 哪条不过补哪条；边界不清类 → **退回 sdd:intake 补澄清**（重入，读 JOURNAL 接着上次继续）
- mode=interactive：三件套交用户确认后定稿；mode=unattended：定稿并回报
- 定稿 → REGISTRY 状态：待实现

**定稿语义**：定稿 ≠ 冻结——它是「此后变更走三分支表」的开关（`sdd:skills/init/references/governance-files.md`）。

### 5. 变更（对已定稿内容）

- **spec 期内**（未 start）：直接修改 + SPEC.md 头部 `version` 自增，不记 AMENDMENTS
- 开发中推翻：**不归本技能**——那是 start 的放弃流程（记 AMENDMENTS → 回退本技能重来）
- 已完结被取代：新需求走 intake 立新提案；AMENDMENTS 记一笔，旧提案冻结

## 常见误区

| 你会想 | 事实 |
|---|---|
| 「范围外显而易见，不用写」 | 范围外不写 = 范围没有定义域，蔓延从第一周开始 |
| 「这条标准先这样，实现时再细化」 | 实现时细化的标准不受契约约束；定稿前是唯一能改的窗口 |
| 「这个任务挺小，两三个合一个提交吧」 | 任务 = 提交粒度是提交纪律的锚；合并后回滚和指认都失效 |
| 「被否的方案不用记，反正不会再用」 | 会。JOURNAL 里的成形记录 + DESIGN 被否备选表双重拦它 |
| 「DESIGN 写到一半方案没定，顺手定一个」 | 探索归 intake——interactive 下技术决策要用户在场；退回补探，不边写边定 |
